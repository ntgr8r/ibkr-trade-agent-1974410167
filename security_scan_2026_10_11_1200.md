# Security Scan Worklist — 2026-10-11 12:00 (America/Mexico_City)

## Scope and current conclusion

This was a read-only static review of the repository, its local configuration metadata, Docker configuration, and frontend dependency advisories. No production credential values were displayed, copied, transmitted, or changed. No broker, LLM, Longbridge, SMTP, or other application API call was made by this review.

The codebase is **not data-isolated by design**. It retrieves broker account data and can disclose selected account/portfolio content to configured third parties. No code-specific evidence of a malicious backdoor or covert author-controlled endpoint was identified in this review. Security decisions must be based on observable code, configuration, deployment controls, and traffic—not an author’s nationality or identity.

## Confirmed data flows

| Flow | Data involved | Destination / control concern |
|---|---|---|
| IBKR Flex download | Statements, account, positions, trades, cash flows | Interactive Brokers Flex Web Service; uses a `FLEX_TOKEN` in request parameters. |
| LLM inference | Prompts can include cash, top positions, recent trades, P&L, account context, and portfolio decision context | Configurable provider URL; the configured provider receives the complete JSON request payload. |
| Longbridge OpenAPI / MCP | Public-market queries and OAuth credentials | Longbridge endpoints; outbound calls use OAuth bearer tokens. |
| Email | Daily reviews and account snapshots, potentially with attachments | Configurable SMTP host and recipients. |
| Elasticsearch / Redis | Local persistence/cache of financial and agent data | Docker publishes both services; Elasticsearch security is disabled. |

  - Evidence: `.env` contains authentication, encryption, internal-token, and Longbridge OAuth configuration keys and is readable by group/others.
  - Acceptance: `stat -c '%a %n' .env` returns `600 .env` and no secret-bearing runtime file is group/world readable.

  - Include: application admin password/session secret, encryption key, daily internal token, Longbridge OAuth client material/tokens, IBKR Flex token, LLM provider API keys, SMTP password, Elasticsearch/Redis credentials if enabled.
  - Acceptance: old values are revoked where supported; replacement secrets are stored outside Git and access is documented.

- [ ] Do not expose Elasticsearch or Redis directly from Docker in any non-local deployment.
  - Evidence: `docker-compose.yml` publishes ports 9200 and 6379, while Elasticsearch explicitly sets `xpack.security.enabled=false`.

- [ ] Require authentication for every route serving account, position, chart, trade-adjacent, or provider-status data.
  - Known unauthenticated data routes include account overview, positions list/summary, charts, Longbridge routes, and market-event routes.

  - Evidence: the default CORS regex accepts arbitrary `http`/`https` origins with credentials; login sets `secure=False`.
  - Acceptance: an explicit origin allowlist is used, wildcard regex is absent in production, cookies have `Secure`, `HttpOnly`, and appropriate `SameSite` settings, and TLS terminates at the deployment edge.

## P1 — reduce outbound personal/financial-data disclosure

- [ ] Establish and approve a data-egress policy before configuring an LLM provider.
  - Policy must identify approved provider domains/accounts, regions, retention/training terms, legal basis, data classification, and an owner.
  - Acceptance: only allowlisted HTTPS endpoints can be configured; the provider cannot be changed to an arbitrary URL by an administrator without a reviewed change.

- [ ] Minimize or redact account context before every LLM call.
  - Evidence: trade-decision contexts include cash, top positions, recent trades, unrealized P&L, and portfolio facts.
  - Acceptance: prompts exclude account identifiers, exact balances, quantities, transaction IDs, and unnecessary history; an automated test asserts the redaction contract.

- [ ] Add outbound network allowlisting at runtime.
  - Allow only explicitly approved destinations such as IBKR, approved LLM provider(s), approved Longbridge endpoint(s), approved SMTP relay, and required market-data sources.
  - Acceptance: blocked-destination tests prove the app cannot connect to arbitrary Internet hosts; DNS and proxy egress logs are retained with secret redaction.

- [ ] Restrict the LLM administrative configuration endpoints to an approved admin role and audit all configuration changes.
  - Acceptance: changes record who/when/old endpoint/new endpoint (with secrets redacted), and provider tests cannot send real account data.

- [ ] Review email recipients and attachments as a financial-data exfiltration channel.
  - Acceptance: recipient allowlist, approval for new recipients, transport encryption, no credentials in emails, and a tested kill switch for all scheduled sends.

- [ ] Constrain Longbridge OAuth scopes to read-only market-data functions and review token file permissions.
  - Acceptance: granted scopes are documented, renewal/revocation procedure exists, and token files stay mode `600`.

## P1 — strengthen application and platform controls

- [ ] Run backend and worker containers as non-root, with read-only filesystems where practical and only the data/config paths writable.
  - Evidence: Dockerfiles do not create or switch to an unprivileged user.
  - Acceptance: `USER` is non-root in production images; a container compromise cannot modify application code or Docker socket.

- [ ] Define secret storage architecture.
  - Replace plaintext `.env` and JSON credential storage with a managed secret store or at minimum host-protected Docker secrets.
  - Acceptance: production secrets are not passed in image layers, source files, command lines, or world-readable files; rotation ownership and cadence are documented.

- [ ] Protect persisted financial data at rest and define retention/deletion rules.
  - Include Elasticsearch indices, Redis, Docker volumes, agent traces, evaluation/replay records, and email-generated artifacts.
  - Acceptance: documented data inventory, retention period, encryption/access controls, backup handling, and verified deletion procedure.

- [ ] Review all unauthenticated health/status responses for environment and provider metadata leakage.
  - Acceptance: external health endpoint returns only an aggregate status; detailed diagnostics require administrator authorization.

## Controlled runtime egress test — completed

- [x] Confirmed the original Compose deployment was active before the test: backend, frontend, worker scheduler, Elasticsearch, and Redis were running. Elasticsearch (9200) and Redis (6379) were exposed on the host, reinforcing the P0 containment priority.
- [x] Stopped the original services without removing containers, volumes, or configuration.

- [x] Ran the backend LLM client against `https://egress-probe.invalid/v1` with a synthetic key and a non-personal test prompt. The client attempted its configured provider endpoint and failed at DNS resolution inside the isolated network.
- [x] Ran the worker IBKR Flex client against `https://egress-probe.invalid/FlexWebService` with a synthetic token and synthetic query identifier. The request attempted only the configured test endpoint and failed at DNS resolution inside the isolated network.
- [x] Removed the temporary isolated network and restored the original services. The initializer completed successfully and the worker scheduler returned to running state.

### Interpretation

The test confirms that these two code paths make outbound requests only when invoked and that Docker internal networking prevents those requests from leaving the test environment. It does **not** prove what the live deployment has previously transmitted, nor does it inspect encrypted production traffic or provider-side retention. Production egress allowlisting and log-based verification remain required.
